Агенттің жұмысы — QA инженердің қолында

Agent 007 автономды орындайтын QA/AQA жұмысы енді skill ретінде қолжетімді. Сапаны тексеретін gate-тер өзгермеді — олар бұрынғыдай детерминды код. Өзгергені: шешімді cron емес, адам бастайды.

11 процедура 23 команда нұсқа 0.1.0 дереккөз juz40-aqa-agent007

01Бұл не және неге керек

Агент тәулік бойы Jira-ны сканерлеп, өзі кандидат тауып, өзі жазады. Бұл күшті, бірақ QA инженерге басқа нәрсе керек: «мынау фичаны қазір тексеруім керек».

Skill дәл осы айырманы жабады. Агенттің білімі — grounding әдістемесі, тест-кейс техникалары, триаж таксономиясы, баг контракты, completion шарттары — процедура ретінде жазылған. Сіз DV кілтін айтасыз, қалғанын процедура жүргізеді.

Ең маңыздысы: сапа тексерісі қайта жазылмады. Coverage, oracle, test-data, independence және evidence gate-тері сол Node кодында қалды. Skill оларды шақырады да, нәтижесіне бағынады. Сондықтан адам арқылы жүрген жұмыс агент арқылы жүрген жұмыстан нашар болмайды.

02Екі драйвер, бір gate қабаты

Агент пен skill — бір жүйенің екі кіру нүктесі. Айырмасы: жұмысты кім бастайды.

03Орнату

Claude Code терминалында екі команда. Логин, токен, клон керек емес.

/plugin marketplace add nurbeki1/juz40-qa-skills
/plugin install juz40-qa@juz40-qa

Тексеру: /plugin list. Жаңарту: /plugin update juz40-qa.

Жұмысқа дайындық — skill өзі жасайды

Қызметкерден жол сұралмайды. Skill қосылған бойда ортаны өзі тексереді: репозиторийлерді іздеп табады, не жетіспейтінін айтады және режимді шешеді.

bash "$CLAUDE_PLUGIN_ROOT/scripts/preflight.sh"
MODEЖағдайНе болады
FULLекі репо + токен дайынбарлық процедура ашық
SETUPрепо бар, npm ci / .env жетіспейдідайын командалар беріледі, кіруін сұрайды
TESTS_ONLYорkестратор репосы жоқтест жазу/жүгірту бар, gate жоқ — нәтиже «тексерілді» деп жарияланмайды
BOOTSTRAPжаңа машинаклондауға нақты нұсқау

TESTS_ONLY режимінің шекарасы ашық жазылған: grounding, тест-кейс жобалау, Playwright жазу және триаж талдауы жұмыс істейді; coverage/oracle аудиті, Confluence жариялау, Jira баг renderer-і және QA жабу шешімі — жоқ. Сондықтан skill «мынау істелді, бірақ gate өтпеді» деп ашық айтады.

04Нөлдік қадам: авторизация

Агентте токендер алдын ала берілген, сұрайтын адам жоқ. Skill-де керісінше — алдымен кіру тексеріледі, жетіспесе жұмыс басталмайды.

Кім кімнің атынан жазады

НұсқаҚалайJira-да кім көрінедіҚашан
Ортақ сервис .envорkестратор репосының токеніagent007тек оқу
Жеке токенәркімнің өз .env-іөз атынанбаг, кейс жариялау, MR
MCP коннектор/mcp → браузерде бір ретөз атынан, токен файлда жоқоқу (CI-да жүрмейді)

Ұсынылатын гибрид: оқу — MCP арқылы, жазу — жеке токенмен. Сонда аудит таза болады: «бұл багты кім ашты» деген сұрақ қалмайды.

06Негізгі ағын: препродта тексеру

Кезекшінің күнделікті жұмысы. Қымбат браузер прогонына дейін арзан аудиттер жүреді — бұл кездейсоқ тәртіп емес.

npm --prefix "$AGENT_ORCHESTRATOR_PATH" run readiness:diagnose
npm --prefix "$AGENT_ORCHESTRATOR_PATH" run qa:full        -- DV-5877
npm --prefix "$AGENT_ORCHESTRATOR_PATH" run verify-feature -- DV-5877 --check

07Триаж — ең қымбат шешім

Тест қызыл болды. Бұл продукт багы ма, тест ескірген бе, әлде тұрақсыз ба? Қате жауап екі жолмен зиян келтіреді: шынайы баг жасырылады немесе бос баг ашылады.

Басты guardrail

Продукт спеканы бұзып тұрса, тестті «жасыл болсын» деп ЕШҚАШАН түзетпе. Күтілетін мәнді продуктің қате мінезіне бейімдеу — багты жасыру. Тестті өзгертуге тек тестте қате екені grounding-пен дәлелденгенде болады.

08Сапа gate-тері нені блоктайды

Бұл тізім skill-дің пікірі емес — детерминды тексерістер. Құласа, кодты түзету керек, gate-ті емес.

GateБлоктайтын жағдайлар
coverageTC ↔ Playwright трассировкасы үзілген: жетпейтін немесе артық кейс, жабылмаған layer. Кейс ID тек негізгі executable кестеден оқылады — coverage matrix, архив, коммент есепке алынбайды
test-qualityassertion-сыз тест; тек HTTP статус тексеретін positive API кейсі; acceptance 5xx; success пен error статусты бір уақытта қабылдау; «500 емес» деген әлсіз шарт; бақыланатын нәтижесі жоқ UI тест
oracle:auditresponse schema мен business инвариант бөлек дәлелденбеуі; requirement → TC → grounded source байланысының жоқтығы; дереккөзде парақ нұсқасы болмауы; postcondition hook-сыз positive mutation; manifest ішінде секрет
independenceserial тәуелділік, mutating beforeAll, кеш shared cleanup. Тізім араластырылып, әр тест жеке жүгіреді, сосын 2 worker × 2 repeat, retries=0
test-dataretry арасында қайталанатын дерек; кепілсіз cleanup; shared entity-ді қалпына келтірмеу; үнсіз .catch()
ui:coveragedeclaration/файл сәйкессіздігі, P0/P1 journey матрицасының бұзылуы, мерзімі өткен quarantine

09Сұйылтуға болмайтын сегіз ереже

Агентте де, skill-де де бірдей. Бұзылса — жұмыс нәтижесі жарамсыз.

  1. Продукт коды, БД, Elastic, Figma — тек оқу. Коммит/пуш жоқ.
  2. Gate-ті жеңілдетуге тыйым — «жасыл болсын» деп әлсіретуге болмайды.
  3. PRODUCT_BUG-ты дәлелсіз STALE_TEST қылуға тыйым. Бұл багты жасыру.
  4. Mobile scope-ты web арқылы жабуға тыйым — handoff.
  5. Тест өзгерісі тек branch + Draft MR. Skill мерж жасамайды.
  6. Сыртқы жазу renderer арқылы. Қолмен description, raw Jira POST — жоқ.
  7. Секретті баспа, сұрама, репоға жазба. Тек env атауы.
  8. Белгісіздікті болжаумен жаппа — UNKNOWN → эскалация.

10Figma сверкасы

Дизайн тексерісі арзаннан қымбатқа жүреді, себебі айырма көбінесе мәтіннен басталады.

  1. Сілтемені спекадан алConfluence-тегі «Дизайн» сілтемесінен. Жоқ болса — бұл product gap, өзің макет іздеп кетпейсің.
  2. Мәтін сверкасыfigma -- texts → тірі беттің мәтіндерімен салыстыру. i18n, copy, батырма атауы, реттілік — суретсіз, детерминды.
  3. Содан кейін визуалfigma -- export + Playwright скриншоты → құрылымдық салыстыру: элемент бар/жоқ, күй, иерархия. Pixel-perfect емес.
  4. ВердиктСпека мен дизайн келісіп, прод басқаша болса — PRODUCT_BUG. Спека мен дизайн бір-біріне қарсы болса — UNKNOWN, екеуі бірдей авторитетті.

Пиксель деңгейіндегі регрессия — басқа механизм: visual:baseline скриншотты бекітілген baseline-мен салыстырады, Figma-мен емес.

11Кезекшінің тізбегі

Үш процедура, нақты осы ретпен. Алдыңғысы құласа келесісінің мәні жоқ.

  1. Орта дайын баreadiness:diagnose — препрод UI, API auth, төрт рөл аккаунты, deploy метадеректері. Құласа себебін өзгертпей хабарла: категория, иесі, әрекет.
  2. Фичаны тексерqa:full -- DV-XXXX → gate-тер → evidence → completion gate. Құлаған тест болса триажға өтеді, автоматты қайта жүгірту жоқ.
  3. Есеп берdaily-report -- --dry әдепкі. Мәтінді көрсетіп, растағаннан кейін ғана жібереді. Есепте не тексерілмегені және неге міндетті.

12Жаңарту қалай тарайды

Дереккөз — орkестратор репосы. Plugin репосы тек тарату арнасы, сондықтан өзгертуді көшірмеде жасауға болмайды.

13Skill нені алмастырмайды

Агенттегі автономия қабаты орнында қалады: тәулік бойы Jira скандау, deployment observer, dedup және cooldown, model routing, CI авто-триггер. Оларды адам қайталамайды.

Сондай-ақ skill шешпейтін нәрселер: native Flutter/mobile тестілеу, тексерілетін oracle-ге айналмайтын exploratory UX шешімдері, performance және security тестілеу жеке дисциплина ретінде, финалды мерж және production deploy, және дереккөздер бірдей авторитетті болған продукт қайшылықтары.

Бұл шектеулер ашық айтылған: процедура «тексердім» деп айта алмайды — артефакт керек.
